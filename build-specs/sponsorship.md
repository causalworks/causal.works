# Sponsorship: build spec

Branch `build/sponsorship`. Migration range 360-379. Budget guide: about half of the available cloud credit; stop at the end of a milestone rather than start one you cannot finish. Read `README.md` first.

## Purpose

A workspace can act as a fiscal sponsor: it holds money for projects that have no charity status of their own, controls how that money is spent, charges an administrative fee, and reports to the projects and their funders. This module covers the whole life of a sponsored project: intake, agreement, money in, fees, requests and payments out, reports and statements, good standing, closing.

## What exists today (extend)

Routes in `server/organizational/routes/sponsored-projects.js` (list, create, change, delete, tracking, create disbursement, approve disbursement; the approve route uses its own middleware and is allowlisted); tables `org_sponsored_projects` (name, description, dates, lead name and email, annual budget estimate, status, model, linked program, admin rate, next report due, last report received, disbursement expense account), `org_sponsored_project_disbursements` (date, amount, admin fee, notes, status, created by, approved by, ledger link); `lib/disbursementPosting.js` (posts an approved disbursement from a bank account to the project's expense account and program, source `sponsored_disbursement`, voidable with reason); gifts can already be tagged to a project (`org_gifts.sponsored_project_id`); documents can already be attached to a project; a setting marks the workspace as a fiscal sponsor so the compliance calendar adds items. The write area `sponsorship` exists.

## Decided rules

1. **A project is a restricted fund.** Its fund is the linked program plus the restriction class on ledger lines; no separate accounts. A gift or grant tagged to a project posts to the project's program with a restricted class automatically (extend the gift-posting code; do not add a second path). In a workspace marked as a fiscal sponsor a gift with no project is flagged for review in Gift Postings.
2. **Project balance is computed by one helper** (`lib/sponsorBalance.js`) used by the project page, statements, request checks, the dashboard flag and reports: received (posted and, separately, unposted), fees accrued and fees posted, disbursed (posted), pending (approved or pending requests and disbursements), available. A line under the balance compares the project's ledger net for its program with the computed figure and shows any difference (follow `lib/receivablesPayables.js` for the pattern).
3. **No spending ahead of money received.** A payment request or disbursement larger than *available* is refused. Only an admin may override, with a reason, and the override is logged and shown on the project. A project that is negative for any reason (late fee, recall) shows a red flag on the sponsor's dashboard. The sponsor never advances its own funds.
4. **Approval.** Whoever creates a disbursement cannot approve it. Above a threshold set in sponsorship settings (default 5,000 dollars), two different people approve. The existing rule that a board member may approve when the small-organization setting is on is kept.
5. **Fees.** A project has a fee rule: percent of gross receipts (default 6 percent, editable up to any value), optional minimum per quarter, optionally tiered, with per-gift or per-grant exemptions (a flag on the gift for funders that cap overhead). Fee is accrued when money is received. It is shown as its own line on the project and statement. A fee rule is locked once the agreement is signed; a change is a dated amendment (new rule row with an effective date and the amendment document), never an edit. Management services the sponsor sells to a project (bookkeeping, payroll, compliance setup, on retainer or hourly) are ordinary sales invoices to the project's contact, not fees.
6. **Fee posting happens in Accounting.** A "Run fees" preview (like fixed-asset depreciation) lists, per project, the fee due for a period not yet posted; a person with Accounting write access confirms; the entry charges the project fund (an expense line on the project's program with the project's restricted class, which the statement of activities already treats as a release) and credits unrestricted administrative fee income. Reversal through the ledger void with a reason. Source `sponsor_fee`.
7. **Project leads do not sign in.** They use scoped single-use-or-revocable links (README, public links) that open: the project's balance and activity, a payment request form, a report form, a document upload. A lead never sees another project. Monthly statements are emailed to the lead.
8. **Payment requests** are the front door for spending: payee (a contact: vendor or individual), amount, purpose, method, attached invoice or receipt, optional link to the approved budget line. The sponsor reviews the request against the balance and the project's approved budget (a warning, not a block, when the request is outside the budget), approves, rejects or asks for more information. Approval creates a disbursement in the existing flow; posting to the ledger remains an Accounting step.
9. **Models.** *Comprehensive*: the sponsor pays the project's bills directly. *Pre-approved grant*: the sponsor releases money as grants to the legal entity the project names (a contact); it needs a signed grant agreement on the release, a W-9 on file before the first release, a release history the project can see, and a year-end sheet of releases (and of noncash items at value) with a flag when an entity reaches the information-return threshold (a setting by year, currently 2,000 dollars; confirm against the IRS instructions each year). Model is chosen per project; a workspace default exists.
10. **Control stays with the sponsor.** The sponsor can place a project *on hold* (all disbursements and requests blocked) with a reason, and can *recall* funds with a reason (a recorded transfer back, through Accounting). A report overdue by more than a setting (default 30 days) puts the project on hold automatically with the reason "report overdue"; clearing the cause lifts the hold, an admin can lift it earlier with a reason.
11. **Documents** attached to a project have types (application, agreement, insurance, report, correspondence, tax form, donor letter) and keep versions; a project without a signed agreement is flagged.
12. **Closing.** Stop new income, pay final bills, then a recorded transfer of the remaining balance, after the sponsor's own liabilities, to one of: the project (now a charity), a new sponsor under a written agreement, or as the sponsor decides under the agreement. The record holds the date, destination, amount, reason and document, and posts through Accounting.
13. **Access.** Reading: admin, finance, board (read only), sponsorship manager; program leads who are workspace users see only their project. Writing: area `sponsorship` as today. Anything that changes money (approve, override, recall, close, fee run) is admin and finance. All with `logAudit`.

## Data model (create or extend; adjust column details to fit the code)

- Extend `org_sponsored_projects`: status values applicant, accepted, active, on_hold, winding_down, ended, lapsed (keep existing values valid); hold reason and hold set by and at; agreement signed at; receiving entity (contact id) for the grant model; W-9 on file flag; good-standing flags.
- `org_sponsor_fee_rules` (project, kind percent, flat or tiered, rate, tiers json, minimum per quarter, effective from, amendment document id, created by).
- `org_sponsor_settings` (one row per workspace): default model, default fee rule, second-approval threshold, overdue-report hold days, donor-letter threshold (default 5,000 dollars), information-return threshold by year, statement day of month, the administrative fee income account, the default program for fee income.
- `org_sponsor_applications` (applicant name and contact, mission, activities, budget, leaders, expected funders, risks, status submitted, in review, accepted, declined, decided by, decided at, reason; project id on acceptance). A public application page is optional; staff may also enter an application.
- `org_sponsor_agreement_templates` (workspace, model, title, body text with merge fields) and `org_sponsor_agreements` (project, template, effective date, term values, generated document id, signed document id, signed at, amendments as child rows with their documents). The template body covers the terms listed under "Agreement terms" below. Generate a PDF with `lib/OrganizationalHtmlPdf.js`; the signed copy is an uploaded file. No electronic-signature feature.
- `org_sponsor_payment_requests` (project, requester link reference, payee contact, amount, purpose, method, status, reviewer, decision reason, disbursement id).
- `org_sponsor_reports` (project, kind: project-to-sponsor quarterly, sponsor-to-funder, period, due date, received at, document id, reminder log). Quarterly reports due within 30 days of quarter end; one calendar with grant reports.
- `org_sponsor_acknowledgments` (project, item key, dated acknowledgment, who) for the list in rule "Standing terms" below.
- `org_sponsor_approvals` (project, kind: funder letter of inquiry, proposal, pledge, agreement, solicitation material, publicity; draft document, approved by, approved at, signed copy document).
- `org_sponsor_closings` (project, destination kind, destination contact, amount, date, reason, document, ledger link).
- `org_sponsor_statements` (project, month, generated document id, sent at; unique project plus month).
- Reuse `org_public_links`, `org_payment_accounts` from the Membership build if present on `main`; if not, build the lead-link milestone last and check again.

All with row-level security; program-limited policies where a table has a project's program.

## Agreement terms the template covers (from common sponsor agreements)

Effective date; sponsor oversight; sponsor control of the date and amount of every disbursement; the sponsor's right to withhold, recall and redirect funds (variance power); gifts are the sponsor's assets; the administrative charge as a percent of gross receipts with an optional quarterly minimum; the sponsor's access to records and its right to audit; quarterly project reports within 30 days of quarter end; limits on lobbying and political activity; the project employs its own staff under the model chosen; indemnity; the sponsor approves proposals, solicitations, publicity and funder agreements, and fundraising materials say the sponsor holds the funds and has variance power; term ending at charity status, 30 days' notice or a fixed date; what happens to remaining funds; amendments in writing; an exhibit holding the board-approved proposal and budget (with the lobbying budget if any). Under the grant model a donor cannot direct a gift to an individual; the template says gifts are to the sponsor for the project's purpose.

## Standing terms each project acknowledges (dated)

No spending before approval is reimbursed; no use of the sponsor's tax number or name for outside accounts; limits on fundraising methods (auctions, social-media drives); rules for work abroad; lobbying and political limits; conflict of interest; insurance in place; annual review. Conditions to stay active: annual report, current fees or dues, lobbying acknowledgment. A lapsed project can be reactivated.

## Milestones (one pull request each)

**S1. Funds, balance and fees.** Migrations for fee rules, settings; `lib/sponsorBalance.js` with tests (every component, the tie-out line, a negative balance); gift tagging posts to the project's program with a restricted class and flags untagged gifts in a fiscal-sponsor workspace; project page shows the balance parts, fee line and the tie-out; fee rule editing with amendment locking; "Run fees" preview and confirm in Accounting with source `sponsor_fee` and its tests (percent, minimum per quarter, exemption, tiered, reversal, locked year).

**S2. Requests, approvals and holds.** Payment requests (staff entry first), review against balance and budget, over-balance refusal and admin override with reason, two-person approval above the threshold, holds and recalls with reasons, the overdue-report automatic hold in a daily job, the dashboard flag for negative or on-hold projects. Tests for every refusal path.

**S3. Intake, agreements, documents, reports.** Applications and the accept-or-decline decision record that creates the project; agreement templates, generation, signed copy upload, amendments; document types and versions; the missing-agreement flag; reports calendar with reminders and a received tick with document; sponsor-to-funder reports; acknowledgments list; approvals queue for items using the sponsor's name; good-standing status and reactivation; compliance calendar items follow these.

**S4. Statements and year end.** Monthly statement per project (opening balance, income, fees, expenses, closing balance) as a PDF through the existing PDF code, stored as a document, emailed to the lead and reply-to the workspace address, idempotent by project plus month, plus a scheduled job; year-end sheet of income and expenses by project that ties to the ledger by fund; donor letter requirement for gifts above the threshold by check, transfer or wire (a template letter and an upload on the gift, flagged when missing); receipts and acknowledgment wording naming the sponsor as recipient and the project as purpose; noncash gift receipt and release as a grant of property at value.

**S5. Pre-approved grant model.** Releasing money to the project's legal entity: entity contact, W-9 flag required before first release, release history, grant agreement attached to each release, year-end sheet with the information-return flag, noncash items. Closing a project with the recorded transfer (rule 12).

**S6. Lead links and optional pages.** Scoped lead links using the shared public module (check `main`; if it is not merged, write against the interface in the README and note it): balance and activity view, payment request form, report form, document upload; an optional public project page with a donate button that opens the hosted payment page when the Membership build's payment provider code is present on `main` (otherwise leave the button out); recurring-gift hook note only.

## Out of scope for this build

Lead sign-in accounts and a portal, built-in electronic signatures, selling services as a separate module, multi-sponsor consolidation. Note any hooks you left in `PROGRESS.md`.

## Acceptance checks per milestone

State in each pull request which of these you ran. Balance: a table-driven test of every component; the tie-out difference explained. Money out: an over-balance request, a held project, an overdue report, a creator approving their own disbursement and a one-signature approval above the threshold are each refused with a plain message; an admin override needs a reason. Fees: each rule type, the minimum, an exemption, reversal, a locked fiscal year. Privacy: a lead link opens exactly one project; a board member reads but cannot change; a program lead sees only their project. Idempotence: running a statement or fee job twice creates nothing the second time.

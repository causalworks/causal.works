# Community Solid Server — Findings & Gaps

A running, append-only reference of things learned about CSS's *actual* behavior — not what's built on top of it. Separate from the internal engineering log, which tells the story of what was built and when: this one is a flat lookup of "here's what we know about CSS that its own docs don't tell you." Useful for future sessions, for the Solid World talk, and for any direct contact with CSS maintainers or the Solid Practitioners Group.

**Add an entry here the moment a CSS behavior surprises us or requires reading source instead of docs — not retroactively.** Retroactive entries lose precision; logged-in-the-moment ones stay accurate and cheap to write.

Format per entry: short title, what we hit, what CSS actually does (with source reference), whether it's documented anywhere official, and whether it's a real product gap worth raising upstream or just a "now we know" note.

---

## WebID-account linking is additive, not a transfer

**What we hit:** attempted to migrate a pod's owning identity from one CSS account to another by linking the WebID to the new account, assuming this would replace the old account's claim to it.

**What CSS actually does:** `POST` to an account's `webId` control link (`.../account/{id}/webid/`) *adds* a link — it does not remove any existing link from another account. After linking, **both** accounts can mint valid client credentials for that WebID. A real, separate `DELETE` on the *old* account's specific link-resource (its own URL, distinct from the webId string itself — found via that account's own `webIdLinks` map) is required to actually revoke the old account's access. Source: verified live against a disposable test pod — linked a new account, confirmed the old account's `webIdLinks` still listed the WebID, confirmed the old account could still mint credentials for it, then confirmed `DELETE` on its link-resource cleanly removed only that one link with no effect on the account's other legitimate links.

**Documented?** Not found anywhere. CSS's own docs and issue tracker cover the *linking* flow (the verification-triple, proof-of-control process — see next entry) but not un-linking or the additive-not-exclusive nature of linking a second account.

**Verdict:** Real gap. Worth raising — "transfer ownership" is a natural operation for any multi-tenant deployment (which CSS explicitly supports, path-based pods being the documented pattern), and the additive default is a genuine footgun: a naive migration script (ours, on the first attempt) can "complete" a transfer while silently leaving the old account with full access.

## No supported "transfer pod ownership" operation

**What we hit:** looked for a first-class "change who owns this pod" API before building a migration procedure.

**What CSS actually does:** no such operation exists. What we assembled instead, entirely from lower-level primitives: (1) register a new account, (2) attempt to link it to the existing WebID, which triggers (3) a verification challenge requiring a specific RDF triple (`solid:oidcIssuerRegistrationToken`, a fresh UUID) to be added to the WebID's profile document by whoever currently controls it, (4) retry the link once the triple is present, (5) separately delete the old account's link (see previous entry). Five manual steps, none of them documented together as "how to migrate a pod."

**Documented?** The verification-triple mechanism itself is real and by-design (CSS returns the exact triple to add, with a helpful message — "You can remove this triple again after validation"), and appears related to community discussion (issue #581 in the CSS repo, per our search) about WebID ownership verification generally. But no combined "here's how you transfer a pod" walkthrough exists.

**Verdict:** Real gap, worth raising, distinct from the additive-linking finding above — even with the additive/unlink behavior understood, there's no supported single operation for what should be a common multi-tenant lifecycle event (an org leaving a platform, credential rotation, etc.).

## `isLinked()` / `WrappedIndexedStorage` internal indexing is not safely hand-editable

**What we hit:** after a bug caused a real credential to be lost (see DevPath rev 56), attempted to directly patch CSS's on-disk internal account-store JSON to restore access, twice, on the reasoning that "just add the link back to the account's own data." Both attempts left the account's own embedded data looking correct on inspection, but `CreateClientCredentialsHandler` still rejected it with `"WebID does not belong to this account"`.

**What CSS actually does:** the `isLinked(webId, accountId)` check (`BaseWebIdStore.isLinked`) doesn't read the account's own embedded data directly — it goes through `WrappedIndexedStorage.find()`, which resolves a query via `findIndexedRoots()`: for each *indexed* field in the query, it looks up a **separate index file** (`.internal/accounts/index/<type>/<field>/<value>$.json`) and intersects the results. We traced and correctly patched the `webId`-keyed index (confirmed present via the source), but access was still refused — meaning at least one more piece of this system's actual matching logic (whether `accountId` is separately indexed, resolved structurally via the parent-relation instead, or something else) was not fully pinned down even after reading three layers of source (`CreateClientCredentialsHandler` → `BaseWebIdStore` → `WrappedIndexedStorage`).

**Documented?** No — this is CSS's internal storage implementation, not a public API or documented data format. Treating it as hand-editable was the mistake, not a missing doc per se.

**Verdict:** Not a product gap to raise upstream (internal storage formats aren't meant to be stable or hand-edited) — but a firm lesson: **never hand-edit CSS's internal account/index JSON as a recovery mechanism.** The reliable recovery path that actually worked was operating at the *resource policy* layer instead (a `.acr` permission) rather than CSS's internal identity bookkeeping — ACP doesn't care which account can authenticate as a WebID, only that a policy names it, which sidesteps this whole fragile internal system entirely.

## ACP: a resource's own `.acr` does not override ancestor `memberAccessControl` — it's a union, not a replacement

**What we hit:** designed our own permission-expiry mechanism (`podPermissions.js`) assuming that once a resource has its own `.acr`, it's fully authoritative for that resource and no longer inherits anything from ancestor containers' `memberAccessControl`. Live testing during an unrelated recovery step contradicted this: a policy added only to the *pod root's* `memberAccessControl` correctly gave access to a document that already had its own separate, more restrictive resource-level `.acr`.

**What CSS actually does:** confirmed via `AcpReader.extractPermissions()` source — for a given target resource, it collects policies from the target's own ACR (`accessControl` field) **plus every ancestor container's ACR** (`memberAccessControl` field, walking all the way to the pod root), and **unions all of them** (`policies.push(...)`, never a replace/break). A resource's own `.acr` adds to inherited permissions; it never excludes them. This matches the actual W3C ACP spec's intent (a pod owner should never be able to lock themselves out via a stray resource-level policy) but contradicts the more restrictive "most specific policy wins" mental model that's common from ACL/filesystem-permission systems.

**Documented?** Implicit in the ACP spec's design if read closely, but not something CSS's own docs call out as a gotcha, and easy to get wrong by analogy to other permission systems.

**Verdict:** Not a CSS bug — correct, spec-conformant behavior — but a real gap in how easy it is to misunderstand. Worth being explicit about in any of our own documentation or talks: **root-level (or any ancestor-level) permissions are always additive and pod-wide**, regardless of what any individual resource's own `.acr` says. Our per-resource permission/expiry design (`podPermissions.js`) is unaffected by this in practice (it was already deliberately explicit about owner access at both levels), but the finding is exactly the kind of thing worth stating precisely if this comes up at a talk.

## WAC and ACP are mutually exclusive per server instance, with no migration tool between them

**What we hit:** needed to switch an existing CSS instance from WAC (its default) to ACP (needed for scoped/purpose-limited permissions) partway through this project.

**What CSS actually does:** the two authorization models are alternate config bundles (`file.json` for WAC, `file-acp.json` for ACP) that bind to the same internal handler slots — a server runs one or the other, never both, and there's no supported way to run mixed-mode even per-pod. They use entirely different on-disk authorization file formats (`.acl` Turtle for WAC, `.acr` Turtle for ACP, different vocabularies) with **no built-in conversion tool** between them — confirmed by checking CSS's own "migration" code, which only covers internal storage-format version bumps, nothing related to WAC↔ACP.

**Documented?** The two bundled configs exist and are documented as alternatives; the *lack* of a conversion path between them on a live server is not explicitly called out anywhere we found.

**Verdict:** Worth raising as a real gap for any team running CSS in production and later needing to adopt ACP's finer-grained model — switching only stayed cheap for us because the affected pods held nothing but synthetic/disposable content at the time (a one-time free window we explicitly closed once real content existed — see DevPath rev 51).

## No CSS API for pod or account deletion

**What we hit:** repeatedly, across this whole project — every disposable test pod and account created for verification purposes (the original pilot org, and roughly a dozen throwaway test/recovery accounts created during the credential-isolation work) had no way to be cleanly removed via any CSS API.

**What CSS actually does:** the account API supports create, login, link/unlink a WebID, create a pod, create client credentials — no delete operation for a pod or an account was found anywhere in the discoverable API surface (`account.controls`) at any point in this project.

**Documented?** Not found. Could exist as an undocumented/internal-only operation, or genuinely not exist yet as a feature.

**Verdict:** Real gap, worth raising — especially for exactly our use case (a platform provisioning per-tenant pods programmatically needs a matching cleanup path for offboarding, not just onboarding). Our own workaround has consistently been either leaving orphaned test pods in place (harmless but accumulates) or, once, careful direct filesystem removal of a decommissioned org's pod content and internal account-store entries (`pod-pilot`, see DevPath rev 52) — which is only viable because we have full filesystem access to our own single-tenant-of-CSS deployment, not something a normal API consumer could do.

## Server-side encryption-at-rest is a clean DataAccessor-level extension point — with two sharp edges

**What we hit:** prototyped transparent AES-256-GCM encryption at rest for CSS's file storage (server-held key, not solving external key management), per an ODI-application ask to have something concrete and honestly-scoped to describe. Built and verified live against a disposable throwaway instance (`/root/css-pod-encryption-prototype/`, port 3097) — never touched the production `css-pod` (port 3001, `data.causal.works`).

**What CSS actually does:** `FileDataAccessor` (`dist/storage/accessors/FileDataAccessor.js`) is the sole seam between the LDP resource store (`DataAccessorBasedStore`) and the filesystem — `getData`/`writeDocument` are the only two methods that touch document bytes; everything else (metadata, containers, listings) is separate. A decorator wrapping `FileDataAccessor` (encrypt in `writeDocument`, decrypt in `getData`, delegate everything else) is a ~120-line class with no changes to CSS's own source. Wiring it in is pure Components.js config: register the decorator as a new component in a small local npm-style module (`package.json` with `lsd:module`/`lsd:components`/`lsd:contexts` fields, a `components.jsonld` — critically needs `"@type": "Module"` and `requireName` at the top level, easy to omit and get a silent "component not found" error with no hint why), then retarget `urn:solid-server:default:ResourceStore_Backend`'s `accessor` property using Components.js's `Override` mechanism (`overrideInstance` + `overrideParameters`) rather than re-declaring the existing `FileDataAccessor` id with a new `@type` (redeclaring produces "Detected multiple values for parameter ... RDF lists should be used"). Also needed: `-m <path>` (`--mainModulePath`) pointed at the *app's own* package root, not left at the default — CSS's bin script otherwise starts Components.js discovery from inside `@solid/community-server`'s own install location and never walks a sibling module that's only listed in the outer app's `package.json`.

Two things were not obvious until live-verified:
1. **CSS reuses the same file-backed `DataAccessorBasedStore` for its own internal bookkeeping** (accounts, IDP keys/JWKS, cookies, migration flags — everything under `.internal/`), not just user pod documents, when both are configured on the file backend (the default `file-acp.json` setup). Overriding `ResourceStore_Backend`'s accessor therefore encrypts *all* of it, including chunks that arrive as plain JS strings rather than Buffers (`Buffer.concat` throws on a string element — needed an explicit `Buffer.from()` coercion per chunk). This is arguably a feature (more at rest is encrypted, not less) but it means "encrypt documents" and "encrypt the whole file store" are the same lever here, not two.
2. **`getMetadata` must not be left as pure passthrough.** `FileDataAccessor.addPosixMetadata` reports `posix:size` from `fs.stat` on the *on-disk* (ciphertext) file. Our AES-GCM framing adds a fixed 28-byte overhead (12-byte IV + 16-byte auth tag) per file, so the on-disk size is always 28 bytes larger than what `getData` actually streams back after decryption. Left uncorrected, the HTTP layer sets `Content-Length` to the ciphertext size; the client then blocks waiting for 28 bytes that never arrive, until keep-alive/socket timeout (observed: every authenticated GET took exactly ~6s instead of tens of milliseconds — looked like a hang, not an error, so easy to misdiagnose as an auth/DPoP problem instead of a metadata bug). Fix: `getMetadata` must subtract the fixed overhead from the reported size for non-container resources before returning.

Once both fixes were in, verified live end-to-end against the disposable instance: PUT/GET round-trip through the normal account+client-credentials+DPoP flow (byte-identical), raw on-disk file confirmed unreadable ciphertext (`xxd`/`grep` on the file finds no trace of the plaintext), container listings, in-place updates, and DELETE all worked with zero awareness that bytes were encrypted, private-by-default access control was unaffected (unauthenticated GET still 401), and an ACP public-read policy on the single document (a real "share link" grant) correctly served the *decrypted* plaintext to an anonymous requester — because ACP evaluates access before the accessor is ever reached; the two layers don't know about each other. The AES key was generated and stored under `keys/master.key` (0600), a sibling directory to `data/`, never inside it and never referenced from any file the data store writes.

**Documented?** No — this exact extension pattern isn't in CSS's own docs, though the community discussion referenced in the ODI brief (storage-layer plugin point) points at the same seam. The two sharp edges above (shared internal-bookkeeping store, `Content-Length` derived from ciphertext size) aren't called out anywhere either.

**Verdict:** Real, reusable pattern — the accessor boundary is small and stable enough that this is a legitimate place to add server-side encryption without forking CSS. For the ODI write-up specifically: keep the framing to *exactly* what was verified. This protects data at rest on disk/backups from anyone with raw filesystem access but no key (verified: raw bytes are ciphertext, `grep`/`strings` find nothing). It does **not** protect against a compromised running server process (the key is loaded into that process's memory and every legitimate request decrypts transparently — verified: this is the point, not a caveat), does not address key management/rotation/HSM-backed keys (explicitly out of scope, single static key file), does not encrypt metadata (`.meta`/`.acr` files pass through this decorator untouched in this prototype — filenames, container structure, and ACP policies are visible on disk in plaintext), and says nothing about encryption in transit (separate, already handled by TLS termination in front of CSS) or about anyone with legitimate application-level access to the pod (auth/ACP is unchanged and unaware encryption exists — a user or share-link grantee who is *allowed* to read a resource reads it exactly as before).

**Upgrade survival:** should survive a CSS *patch/minor* version bump untouched, since it depends only on the public `FileDataAccessor`/`DataAccessorBasedStore` shapes and the documented Components.js config mechanism (Override, component registration) rather than any CSS internals or forked source. It would break, and need re-verification, on any CSS release that changes `FileDataAccessor`'s method signatures, renames/restructures the `urn:solid-server:default:ResourceStore_Backend` config wiring, or changes how internal bookkeeping storage is backed (e.g. if a future CSS version separates `.internal/` onto its own non-file-backed store, edge case 1 above would need re-checking either way). Nothing here forks or patches CSS's own package files, so a version bump is a `npm install` + smoke-test, not a merge-conflict.

### Follow-up stress test (2026-09-06): large files, range requests, interrupted writes

The original prototype only proved correctness on small documents. Gemini flagged three specific risks worth checking before the design gets described as done; all three were tested live against the same disposable instance.

**Large files — real problem, fixable but not yet fixed.** The accessor fully buffers each document into memory on both `writeDocument` and `getData` (`Buffer.concat` over collected chunks) rather than streaming through the cipher. Verified with real transfers: a 300MB file peaked the server process at ~1.19GB RSS (≈4x); a 600MB file peaked at ~2.72GB RSS (≈4.5x) — both round-tripped with byte-identical SHA-256 checksums, no corruption, no hang, no crash. But the scaling is linear and the multiplier is real, not noise: on this VPS (7.6GB total RAM, shared with the production `css-pod`), a file in the 1.5–2GB range would be expected to push a single request's peak past what's available and risk an OOM kill of the server process. **Verdict: not a correctness bug (nothing observed corrupts), but a real availability risk for large files, and it's the direct trigger for Gemini's chunked-encryption suggestion.** Fixable, but non-trivial: true fix is streaming AES-256-GCM in fixed-size chunks (each with its own nonce and auth tag, or a scheme like AES-GCM with a STREAM construction / `age`'s chunked format) rather than one cipher context over the whole file — this is a real rework of `EncryptingFileDataAccessor`, not a one-line patch, since GCM's single auth tag is inherently a whole-message primitive.

**Partial/range requests — currently a non-issue for Causal's own app, and CSS handles it correctly (if wastefully) regardless.** Grepped `podClient.js` and the document routes: nothing in Causal's app today issues an HTTP `Range` request against a pod document — this is a non-issue for current usage, not a latent bug waiting to bite. Independently, traced how CSS itself handles `Range` when a client does send one: `BinarySliceResourceStore` (wired in by default, sitting *above* our accessor in the store stack — `config/storage/middleware/default.json`) calls `getRepresentation()` on its source **first**, unconditionally, and only slices the resulting stream afterward. That means our accessor's `getData()` always fully decrypts the entire file before any slicing happens — a 1-byte range request against a 600MB file still pays the full ~2.7GB decrypt cost. Verified live: a `Range: bytes=100-199` request against a 50MB file returned the correct 206 response with the exact expected 100 bytes (`Content-Range`/`Content-Length` both correct, byte comparison passed). **Verdict: pass on correctness, real inefficiency once anything does start requesting ranges (e.g. PDF preview or video streaming) — the same streaming rework that fixes the large-file problem would also fix this, since a chunked format could let the accessor decrypt only the requested chunk range instead of the whole file.**

**Interrupted writes — real data-loss bug, and it's a config-level fix, not a code-level one.** Simulated a real crash: seeded a document with known-good content, started a large overwrite, and sent `SIGKILL` to the server process mid-write. Root cause: this pod's config uses the plain `FileDataAccessor`, not `AtomicFileDataAccessor` — `writeDataFile` pipes straight into a `createWriteStream` on the *final* resource path, no temp-file-plus-rename. Confirmed live: killing the process mid-overwrite left the file truncated at the byte count reached at kill time — the old good version was gone (already overwritten in place) and the new version was incomplete. Restarting the server and issuing a `GET` failed loudly and correctly — `500`, `"Unsupported state or unable to authenticate data"` (the GCM auth-tag check catching the truncation) — not silent corruption served to a client. That auth-tag check is actually a small net *win* over plaintext CSS: an interrupted write against an unencrypted resource on this same non-atomic backend would leave truncated plaintext that gets served as if it were valid, silently, with no integrity check at all. But the data itself was still gone either way. **Fix, verified live:** pointed `EncryptingFileDataAccessor`'s `source` at an `AtomicFileDataAccessor` instance instead of the plain one (config-only change — `rootFilePath`/`tempFilePath` wired the same way CSS's own `quota-file.json` already does it, zero changes to our own accessor code, since both implement the identical `DataAccessor` interface). Re-ran the identical kill-mid-write scenario: the write now lands in `.internal/tempFiles/` and only gets renamed onto the real path on full success — killing the process mid-write left an orphaned temp file and the resource's real path completely untouched at its old value. Restarted the server, `GET` returned the original good content, byte-identical. **Verdict: real bug in the as-first-prototyped config, already fixed and reverified — recommend the atomic-accessor wiring becomes the default for any non-throwaway build of this, not an optional hardening step.**

**Net read for the ODI framing:** two of three risks are real (large files, interrupted writes); one is fixed today (interrupted writes, via config) and one is an acknowledged, scoped-but-not-yet-built rework (large files, needs chunked encryption — the range-request inefficiency piggybacks on the same fix). Neither is a silent-corruption story in the version now running: every failure mode observed either round-tripped correctly or failed loudly.

### Key management follow-up (2026-09-06): what "fetch the key from an external service" would actually take

Investigated moving the AES key off local disk to a self-hosted key service (Gemini's "Option A") — scoped only, nothing built. No existing secrets-manager infrastructure exists anywhere in this codebase to build on (grepped for Vault/Infisical/KMS references — none found; the current pattern everywhere, including this prototype's key file, is a static `.env`/flat-file secret loaded once at process start).

**Realistic minimal self-hosted option:** HashiCorp Vault OSS (Docker image, runs fine on the same Hetzner VPS or a second small one — no cloud-provider lock-in). Minimal shape: Vault's KV v2 engine holds the raw key; the app authenticates via AppRole (a role-id plus a short-lived secret-id) and fetches the key once at CSS startup instead of `fs.readFileSync`. New pieces beyond today: a Vault container to run and keep patched, its own storage backend to back up, an unseal step after every restart (Vault starts sealed and needs Shamir unseal keys applied before it will serve anything — self-hosted without a cloud auto-unseal integration means either a manual step after every restart or accepting that operational friction as a standing cost), and AppRole credential bootstrapping. That last point matters: the app still needs *some* local secret to authenticate to Vault — the design moves the static-file problem, it does not eliminate it, though the thing now sitting on local disk is a narrower-scoped, revocable AppRole credential rather than the AES key itself.

**Timeline:** realistic to prototype before Sept 30 — Vault-in-Docker plus KV v2 plus AppRole plus wiring `getKey()` to an HTTP fetch is a few days of focused work, not a rearchitecture, and it composes with the existing accessor unchanged (only `getKey()` changes).

**What it would and wouldn't change, compared to today's static-key file:** it protects the key against anyone with only filesystem/backup access to the app server who lacks Vault access too — a real, narrower improvement over a key sitting in a plaintext file in `keys/`. **It does *not* close the "compromised running server" gap, and this needs to be stated plainly rather than implied away in the ODI write-up:** in this Option A shape, the key is still fetched once and cached in the running Node process's memory for that process's lifetime (exactly like today, just sourced differently at boot) — a compromised running server process can still be made to dump its own memory and recover the key, because the actual encrypt/decrypt operations still happen inside that process using that resident key. Closing the compromised-server gap for real requires a materially different and heavier design (Vault's *Transit* secrets engine used as encryption-as-a-service: the app sends plaintext to Vault per operation and Vault returns ciphertext, so the raw key never enters the app process's memory at all) — that's a bigger scope than "fetch the key at startup," adds a network round-trip to every read and write, and makes Vault's own availability a hard dependency for the whole app. Worth scoping separately if the ODI application wants to claim that stronger property; Option A alone should not be described as solving it.

### Rebuild (2026-09-06): chunked streaming encryption (libsodium `crypto_secretstream`) + per-file envelope keys via OpenBao Transit — supersedes the two limitations above

Both real problems identified in the stress test (large-file memory scaling, and the static-key design only narrowing rather than closing the compromised-server gap) are fixed in this rebuild. Verified live end-to-end against the same disposable throwaway instance; production `css-pod` was never touched.

**Part 1 — chunked streaming, using a ready-made implementation rather than hand-rolled STREAM.** Used `libsodium-wrappers`' `crypto_secretstream_xchacha20poly1305` rather than implementing the STREAM construction by hand. Reasoning: STREAM's actual security depends on subtle details (deriving each chunk's nonce from a running counter, chaining authentication across chunks so one can't be lifted from its position, forcing an explicit end-of-stream marker so truncation is provable) that are exactly the kind of thing a from-scratch implementation gets subtly wrong under time pressure; `crypto_secretstream` is that construction already implemented and audited inside libsodium, with the three required properties (never-reused nonces, chunk-order authentication, detectable truncation) built in rather than left to our own logic. 1MB plaintext per chunk, 17-byte Poly1305 tag + 1-byte type tag per chunk (`ABYTES`), 24-byte header once per file (kept as the first bytes of the ciphertext itself, not duplicated in metadata — it isn't secret, its only job is framing). One real bug found and fixed during this build: the header was initially *also* being duplicated into resource metadata and never actually consumed back out of the ciphertext stream on read, silently misaligning every chunk boundary — caught immediately because CSS's own internal account-cookie storage (which goes through this same accessor) started failing to authenticate on the very first live test. Fixed by making the ciphertext file itself the single source of truth for the header.

**Part 2 — OpenBao Transit, not HashiCorp Vault, verified live before building on it.** OpenBao ([openbao.org](https://openbao.org), Linux Foundation, forked from Vault after Vault's license change and IBM acquisition) was substituted per instruction, and its Transit API was checked against Vault's documented behavior rather than assumed compatible. Confirmed live: `POST transit/datakey/plaintext/<key>` and `POST transit/decrypt/<key>` return byte-identical JSON shapes to Vault's (`data.plaintext`, `data.ciphertext`, `data.key_version`), ciphertexts keep the same `vault:v1:...` wrapping prefix, the `X-Vault-Token` header name still works, and HCL policy syntax (tested with a real least-privilege policy scoped to just `datakey`+`decrypt` on the one named key, denying reads of the master key and denying rotation — both confirmed to 403 correctly) is unchanged. Two real, non-functional divergences found: `sys/mounts` returns `204` with an empty body on OpenBao versus a JSON body on Vault, and issued tokens keep the older `s.` prefix rather than Vault's newer `hvs.` prefix (OpenBao forked before that Vault format migration). Neither affects this integration, since neither field is read by our code — but both are exactly the kind of divergence that would be invisible until checked live, matching the instinct to verify rather than trust the docs.

Design (envelope encryption, matching Vault/OpenBao's own standard "generate data key" pattern): one fresh 256-bit data key requested from OpenBao per file *write* (`datakey/plaintext`, one call), used locally to drive `crypto_secretstream`'s chunk encryption, then explicitly zeroed from memory (`sodium.memzero`) the instant `init_push` has derived what it needs from it — OpenBao's own wrapped form of that same key (useless without OpenBao access) is stored as ordinary resource metadata (the `.meta` file), never the raw key. Reads mirror this: the wrapped key from metadata goes to OpenBao's `decrypt` endpoint (one call), the returned plaintext key drives `init_pull` and is zeroed immediately after. OpenBao never sees a chunk, a byte of file content, or is called more than once per read or write, regardless of file size — confirmed directly via OpenBao's own audit log and accessor-level tracing on a 400MB transfer: exactly one `datakey` call for the write, exactly one `decrypt` call for the read, of that resource. (Honest caveat found during that same trace: CSS's own request-handling touches *other* resources per incoming HTTP call — `.acr` authorization-policy files at each ancestor container, the WebID profile card for auth re-verification, internal account bookkeeping — and because this accessor is wired in at the `ResourceStore_Backend` level, encrypting *everything* the file backend stores, each of those ancillary reads is also a separate, real OpenBao round-trip. The "one call per file operation" claim is exactly true for the resource actually being read or written; it is not the same as "one call per client HTTP request," and the ODI framing should say the former, not imply the latter. Scoping encryption to only user-uploaded pod documents rather than the whole backend would remove this overhead; not done here since narrowing scope wasn't part of this task.)

**Stress-test re-run, same standard as before:**
- **Memory, flat regardless of size — confirmed.** 300MB: baseline ~249MB RSS, peak ~252MB (essentially noise). 600MB: baseline ~252MB, peak ~253MB. 1.8GB (the exact size that would have pushed the old whole-buffering design toward OOM on this 7.6GB box): baseline ~210MB, peak ~243MB. All three round-tripped with byte-identical SHA-256 checksums. The only failure encountered at 1.8GB was unrelated to encryption or memory: CSS's own default write-lock expiry (6 seconds, `WrappedExpiringReadWriteLocker`) aborted the write because encrypting-and-writing 1.8GB took longer than that — a pre-existing CSS constraint that would trip for a plaintext write of the same size on the same disk, fixed by raising `expiration` in config (to 120s), after which the identical 1.8GB write succeeded cleanly.
- **Corrupted/truncated file — rejected, not silently served, confirmed two ways.** A file truncated mid-chunk (cutting into a chunk's MAC) and a file truncated exactly at a chunk boundary (the final chunk missing outright) were both tested. Both fail loudly: CSS's `BasicResponseWriter` logs "Aborting streaming response because of server error; headers already sent" and terminates the connection — the client experiences a terminated/incomplete transfer, never a false "200 complete" with truncated content. The boundary-exact case correctly hits the accessor's own explicit "ended without a final-chunk marker" check; the mid-chunk case correctly hits `crypto_secretstream`'s own authentication failure.
- **Swapped/reordered chunks — rejected, confirmed two ways.** A chunk from one file's ciphertext spliced into another file's ciphertext at the same position: rejected (`crypto_secretstream_xchacha20poly1305_pull` returns `false` on that chunk, since its key-derivation chain belongs to a different header/key entirely). Two chunks reordered within the *same* file: rejected immediately (the chained per-chunk state expects chunks in original order; the swap fails to authenticate on the very first read, even before the response would otherwise have started streaming). No custom detection logic was needed for either case — `crypto_secretstream`'s chained authentication provides it for free, exactly per the ask.
- **Interrupted-write fix — still holds, confirmed unchanged.** Re-ran the identical kill-mid-overwrite scenario (`AtomicFileDataAccessor` as the wrapped `source`, real `SIGKILL` mid-write of a 700MB overwrite) against this new streaming+OpenBao accessor. Same result as before: the write lands in `.internal/tempFiles/`, the real resource path is untouched by a mid-write kill, and a restart serves the original good content byte-for-byte. The interrupted-write fix lives entirely in *which accessor is wrapped*, not in the encryption logic layered on top of it, so it composes cleanly with this rebuild.
- **OpenBao round-trip count — confirmed exactly once per file operation, independent of size**, per the accessor-level trace and audit-log check above; see the honest caveat in the same paragraph about ancillary CSS-internal resource reads adding their own separate round-trips.

**Updated honest scope statement (replaces the "narrows, doesn't close" framing above for this version):** this version genuinely closes the "compromised running server" gap **for any file not actively being read or written at the moment of compromise.** The reasoning, stated precisely for reuse in the ODI application: at rest, a file's plaintext key exists nowhere — not on disk, not in the app process's memory — because it is zeroed immediately after each individual operation completes; only OpenBao's *wrapped* form of that key sits in the file's metadata, which is cryptographically useless without a live, authorized call to OpenBao itself. An attacker who compromises the running CSS process and dumps its memory captures, at most, whatever key is transiently resident for whatever single file happens to be mid-read or mid-write at that exact instant — every other file's key was already zeroed and is not recoverable from that process's memory at all, only by also compromising OpenBao (a separate, independently-securable service with its own narrower, revocable, non-rotating-the-master-key access token). This is a materially stronger and different claim than the prior static-key or fetch-at-startup-and-cache designs, both of which kept every file effectively decryptable for as long as the one long-lived server-held key remained resident — under either of those, a single memory dump at any moment recovered the key for the *entire* pod's contents, past and future, not just whatever was being touched right then. What this still does not protect against, stated with the same care as before: an attacker with a *sustained* compromise who waits for and captures each file's key at its moment of use (this narrows the attack to "must be watching in real time, per file," it does not require zero compromise-time exposure to reach zero risk); a compromise of OpenBao itself (a new, separate attack surface that did not exist in the static-key design, traded deliberately for the property above); loss or corruption of OpenBao's own master key (with no export/backup by design, losing it makes every wrapped key — and therefore every file — permanently unrecoverable, a real availability risk to weigh against the confidentiality gain); and, unchanged from every prior version, metadata/filenames/container structure (visible in plaintext `.meta`/`.acr` files) and anyone with legitimate application-level read access to a resource (auth and ACP are unaware encryption exists, by design).

### Master-key backup/recovery investigation (2026-09-06): what's real, what's currently configured, and what a small team can actually operate

The gap flagged in the scope statement above — "loss or corruption of OpenBao's own master key... makes every wrapped key permanently unrecoverable" — was investigated directly rather than assumed. Investigation only; nothing was changed on the running dev instance or built. All of the following was confirmed live against real OpenBao processes (a fresh non-dev instance with file storage, disposed of afterward), not read off documentation.

**What OpenBao does by default (real, non-dev init) — confirmed live.** `bao operator init` against a genuinely fresh instance produced 5 Shamir key shares with a threshold of 3, and printed, verbatim: *"Vault does not store the generated root key. Without at least 3 keys to reconstruct the root key, Vault will remain permanently sealed!"* This is exactly the split-custody pattern asked about, and it is the literal out-of-the-box default for a real init — not an opt-in feature that needs enabling. Verified both directions: unsealing with exactly 3 of the 5 printed keys worked (confirmed via `bao status` showing `Sealed: false`); resealing and trying with only 2 of the 5 left it provably sealed (`Unseal Progress 2/3`, stuck) and refusing all real operations (`503` on a live API call) — there is no fallback, no back door, no "just enough" partial functioning. `key-status` and the full `operator` subcommand list were also checked for any way to export the raw root key as a single artifact: there is none, by design (`generate-root` creates a new *root token* — an API auth credential — not the root/master encryption key; `rekey` explicitly requires the instance to already be unsealed with a valid quorum of existing shares, so it cannot help *recover* from a below-threshold loss, only *reshuffle* shares while healthy).

**What's actually running on our instance today: the fragile default, exactly as suspected.** `openbao-dev` (the instance backing the encryption work above) was started with `server -dev`, OpenBao's development convenience mode. Dev mode auto-generates and auto-applies a *single* unseal key with no splitting, no threshold, and no separate custody at all — strictly weaker than even a minimal real init, and explicitly self-described in its own startup banner as "should NOT be used in production." This is not a partially-hardened setup that just needs its threshold tuned; it is the one-copy-in-one-place failure mode the question was asking about, currently live. Moving off dev mode to a real `bao operator init` is a precondition for calling this production-ready, independent of any decision about share count below.

**Is there a way to back up the master key material itself, separate from day-to-day operation? Two distinct questions, two different answers, both confirmed live:**
- *The root/barrier key* (the thing Shamir splits): there is no separate backup artifact for this, and there deliberately cannot be — the whole design point of Shamir splitting is that the reconstructed key is never allowed to exist as a single persisted copy anywhere, including inside OpenBao's own storage. The Shamir shares *are* the backup mechanism; there is no second, simpler one sitting alongside it to fall back on.
- *The transit engine's own key* (`css-pod-file-keys`, the one actually used per-file by our accessor): Vault's public documentation describes a `transit/backup`/`transit/restore` pair specifically for exporting a transit key in a portable, still-wrapped form. Tested live against both our real dev instance and a fresh non-dev instance, including first enabling the key's `allow_plaintext_backup` flag as the docs require: the endpoint returns `405 Method Not Allowed` / `"unsupported operation"` on OpenBao 2.1 in both cases. This matches a real, worth-flagging-precisely divergence: transit key backup/restore is Vault *Enterprise* functionality that OpenBao, as a genuinely open-source-only fork, does not carry over. Anyone reading Vault's docs and assuming this escape hatch exists on OpenBao would be wrong — confirmed by testing, not by reading a changelog.

**What this means in practice: two separate layers both have to be covered, and neither one alone is enough.** (1) The storage backend itself (the actual bytes on disk, holding everything OpenBao manages in barrier-encrypted form, including the transit master key) needs an ordinary, conventional backup process — a file/snapshot copy, taken regularly, stored securely off the server. This is unglamorous and has nothing to do with Shamir. (2) Separately, enough Shamir shares (at or above threshold) need to survive in genuinely independent custody, or that storage backup — however current and however carefully kept — is permanently unreadable ciphertext forever. Having one without the other is a false sense of safety: shares alone with no storage backup means nothing to unseal if the server is destroyed; a storage backup alone with too few surviving shares means an intact but permanently locked box.

**Honest assessment for a small team without dedicated security staff.** The textbook version of this — 5 independent long-term human keyholders, each durably and reliably custodying one share for years, reachable and cooperative in a real emergency, with no collusion risk — is very unlikely to be something Causal's current size can actually operate correctly. A team without that many genuinely independent trusted long-term parties who would end up as real distinct custodians risks the shares collapsing back into one or two people's hands in practice (e.g., all shares living in the same person's password manager because there was no one else to hand them to) — at which point the arrangement provides the *appearance* of split custody without the actual property, which is worse than an honest single-key setup because it invites false confidence. The more honest and more likely-to-actually-be-followed recommendation for this team's actual size: a smaller threshold (2-of-3 rather than the default 3-of-5) with separation defined by genuinely distinct *custodial locations*, not headcount that doesn't exist — for example, one share in the operator's personal password manager, one in a truly separate offline location (a physical printout in a safe deposit box, or with a lawyer/accountant who already holds other sensitive business material for the org), and one with a single trusted secondary contact (a co-founder, technical advisor, or similarly positioned person, with written instructions for what it's for and when to use it). This still means no single lost or compromised location is fatal on its own — the actual property being asked for — without pretending an organizational structure exists that doesn't. Whatever threshold is chosen, it needs to be paired with the separate, ordinary storage-backend backup process above, and — because this only matters in a genuine emergency, which is exactly when institutional memory is weakest — a short, written runbook naming where each share lives and the exact commands to run, checked periodically (e.g. as part of an annual review) to confirm the named custodians and locations are still current and the shares still work.

### Real setup + live disaster-recovery drill (2026-09-06): dev mode retired, 2-of-3 Shamir in place, restore verified end-to-end

Following the investigation above, the fragile dev-mode instance was retired and replaced with a real one, and — rather than treating the recovery plan as correct because the mechanism was individually verified in isolation — a full disaster-recovery drill was run against real data.

**Real init, 2-of-3.** `openbao-dev` was removed; a persistent `openbao` container (`--restart unless-stopped`, file storage at `/root/openbao/data`, config at `/root/openbao/config`) replaced it on the same port. `bao operator init -key-shares=3 -key-threshold=2` produced exactly 3 shares needing 2. Verified live, matching the investigation's methodology exactly: 2 of the 3 (keys 1+2) unsealed it cleanly; resealing and trying with only 1 (key 3 alone) left it provably and permanently stuck (`Unseal Progress 1/2`, `503` on a real API call). Transit engine, the `css-pod-file-keys` master key, the least-privilege policy, and a fresh scoped app token were recreated from scratch on the new instance (a fresh init starts with none of this — only a default unrelated `secret/` KV mount).

**Backup automation.** `/root/openbao-backups/backup-openbao.sh`, cron'd nightly at 03:00, tars `/root/openbao/data` with a timestamp and a `.sha256` checksum file into `/root/openbao-backups/snapshots/`, pruning anything older than 30 days. Deliberately does **not** add its own encryption layer: the storage backend is already barrier-encrypted by OpenBao itself and meaningless without 2 of the 3 unseal keys, so a second layer of secrecy on top of the backup file would be solving a problem that doesn't exist here — the actual gap is custody of the 3 key pieces, not confidentiality of the backup bytes. Honestly flagged rather than glossed over: the script only writes to a separate directory on the **same** server today (an `OPENBAO_BACKUP_REMOTE_DEST` hook exists for a real off-server destination, but none exists yet to point it at) — this protects against local corruption/accidental deletion, not loss of the server itself, and is called out explicitly in both the script's own comments and the runbook as an open item, not silently left implicit.

**Runbook.** `/root/openbao-backups/RUNBOOK.md` — plain-language, covers the routine case (server restart, 2 of 3 holders each run one `unseal` command) and the disaster case (fresh machine, restore from backup, unseal, confirm a real document decrypts before calling it done), a table for where each of the 3 pieces lives (left for the operator to fill in — deciding real-world custodians was explicitly out of scope for this build), and an annual-review checklist. Key-piece distribution itself (Part 2 of this build) was handed to the operator directly rather than attempted here — assigning real people/locations as custodians isn't something to script or assume.

**The drill, not just the pieces in isolation.** Rather than trusting that "2-of-3 unseals" plus "a backup script runs" would compose into a working recovery, the whole chain was run for real: (1) a real document (`drill-target.txt`) was written through the full CSS+accessor+OpenBao pipeline against the live instance; (2) a real nightly-format backup was taken and its checksum verified; (3) the backup was extracted onto a **totally separate, freshly-created container** with empty storage — simulating new hardware, not a copy of the same instance; (4) the restored instance came up sealed (as expected — restoring data does not auto-unseal) with its 2-of-3 configuration intact; (5) it was unsealed using a **different pair** of the 3 keys (1+3, not the 1+2 used earlier) than the pair used in the isolated mechanism test, to rule out a fluke tied to one specific pair; (6) the transit master key and the least-privilege policy both survived the restore correctly — confirmed not just by the key being present, but by the scoped app token correctly still being *refused* when it tried to read the master key directly (`403`, policy intact) while still being *allowed* to unwrap a real wrapped key (`200`); (7) the actual wrapped key was pulled from `drill-target.txt`'s real on-disk `.meta` file and unwrapped via the recovered instance; (8) finally, the running CSS server was pointed at the recovered instance's address (data directory untouched throughout) and issued a real authenticated `GET` — it returned the original plaintext, byte-for-byte, through the complete stack, not just at the raw Transit-API level. The live `openbao` instance and its data were never touched by the drill; only the disposable recovery-target container and its extracted copy were used, then torn down afterward.

**Verdict:** the recovery plan is not theoretical — it was exercised for real, once, successfully, including the parts that could plausibly have quietly diverged (does a restored instance really preserve the threshold config and the scoped policy, not just the raw key material; does a different pair of shares really work, not just the specific pair from setup; does the whole application stack actually recover, not just the Transit API in isolation). The one honestly-still-open piece is the off-server backup destination — the mechanism and the hook for it exist, but nothing is currently pointed at real separate infrastructure, and that gap is written down rather than left to be discovered later.

### Key custody status (2026-09-06): currently single-custody, by deliberate choice — not yet real split custody

The three Shamir key pieces and root token generated during the disaster-recovery drill above are, for now, being kept together by Guy in a single file, not distributed to three separate locations as the recovery design calls for.

This is a deliberate, reasoned decision, not an oversight: the platform currently holds no real org data — only demo/test content — so the actual risk of single-custody today is losing access to disposable material, not a nonprofit's real financial or compliance records. Starting with single custody during a pre-launch, single-operator phase is also a normal, common bootstrapping pattern for this kind of system generally, not a shortcut unique to this build.

This status is explicitly temporary and must change before the platform's first real org is onboarded — not on a calendar date, not "eventually." At that point, the three pieces need to actually move to genuinely separate custody (per the recommendation above: the operator's own password manager, a truly separate offline location, and one trusted secondary contact), and this entry should be updated to reflect that it's been done, with the date.

**Trigger to re-check this entry: the first live org signing on to the platform.** If that happens and this section still says "single-custody," treat it as a real gap to close immediately, not a historical note.

### Rekey (2026-09-06): fresh 2-of-3 split issued, old pieces confirmed dead — plus two real gotchas found live

The three key pieces and root token shown in the disaster-recovery-drill conversation were treated as burned (having appeared in chat) and replaced via a real `operator rekey` + `generate-root`, rather than left in place on the theory that "no one else saw them."

**Rekey, verified live the same way as the original setup.** `sys/rekey/init` with `secret_shares:3, secret_threshold:2`, authorized by submitting 2 of the *old* keys (rekey requires an existing quorum to authorize generating a new one — it cannot run from a fully-sealed or key-less state). The 3 new shares were captured directly into a permissions-restricted file via the HTTP API (never printed to any terminal output, split into three separate destination files by a short script, then the combined intermediate file was shredded) rather than via the interactive CLI, specifically so the new material was never displayed together in one place, matching how it needs to be handled going forward. Verified exactly like the original setup: resealing and trying 2 of the *old* keys failed with `cipher: message authentication failed` (the reconstructed key from stale shares no longer matches the current keyring) — old material is genuinely dead, not just "not shown again." Unsealing with 2 of the *new* keys worked cleanly.

**Root token reissued the same way, via the quorum-gated `generate-root` ceremony** (not simply asking the still-valid old root token to mint its own replacement) — `sys/generate-root/attempt` → submit 2 unseal keys → decode the resulting token locally against the one-time pad, again writing straight to a restricted file rather than through visible output. The old root token was then explicitly revoked via `auth/token/revoke`, and confirmed dead (`403` on a real API call with it afterward).

**Real gotcha #1: revoking the old root token cascaded and silently killed the app's own scoped token too.** The `css-encryption-accessor` token used by the CSS accessor had originally been created as a *child* of the root token (`auth/token/create` under that root token's auth context, not `create-orphan`). Vault/OpenBao's default `token/revoke` recursively revokes descendants unless the child was created as an orphan — so revoking the old root token took the app's own working credential down with it, discovered immediately because CSS started failing real requests with `403 permission denied` on `transit/decrypt`. Not a bug in OpenBao — this is Vault's documented default token-hierarchy behavior — but a real operational trap for exactly this kind of "rotate the root token periodically" maintenance, easy to not notice was even a risk until it happens. **Fixed and now the default going forward:** the app's scoped token was reissued via `auth/token/create-orphan` (confirmed `"orphan": true` in the response) — a future root-token rotation will not be able to take it down again, by construction, not by remembering to be careful next time.

**Real gotcha #2: rotating the token file on disk did not take effect until the CSS process was restarted.** `OpenBaoClient.getToken()` reads the token file once and caches it in memory for the process's lifetime (deliberately, to avoid a disk read on every single request) — after fixing gotcha #1 and writing the new orphan token to the same file path the accessor reads from, requests kept failing with the *old* (already-dead) token until the CSS server process itself was restarted. Not a bug — this is exactly the tradeoff of in-memory caching stated plainly in the code — but a real, worth-recording operational fact: **rotating this app's OpenBao token is not hot-reloadable; it requires restarting the CSS process**, the same way `CSS_POD_ADMIN_EMAIL`/`PASSWORD` changes already require a restart per this project's own server-restart conventions.

**Verdict:** the rekey itself is exactly what it should be — old material verifiably dead, new material generated and handed off without ever appearing together in one place. Both gotchas found were caught immediately by re-running the same end-to-end real-document check used throughout this work (never assumed "the API call succeeded, so it's fine") — worth treating as a standing reminder that a credential-rotation operation isn't actually complete until the *consuming application* is re-verified against the new credential, not just the identity/secrets system itself.

## Adjacent, not CSS itself: our own WebID-selection bug (context, not a CSS gap)

Logged for the pattern, not because it's a CSS issue — this was our own code.

**What we hit:** `podClient.js`'s `getAuthenticatedFetch()` originally picked `Object.keys(webIdLinks)[0]` — an arbitrary WebID — when minting client credentials, rather than the one matching the specific pod being accessed. Worked by accident while only one pod existed under our fixed admin account; would have silently 403'd every request against any *other* pod the moment a second one existed.

**What this reflects about CSS, indirectly:** an account holding multiple pods (and therefore multiple WebIDs) is a fully real, supported CSS scenario — confirmed live, an account that's created several pods ends up with one distinct WebID per pod in its own `webIdLinks` map — but nothing in CSS's own API responses flags "you probably want to disambiguate which one you mean" for a caller naively taking the first entry. Not a CSS bug (the API correctly returns all the links; using them correctly is the caller's job), but the multi-pod-per-account case felt under-signposted for how easy it is to get wrong.

**Verdict:** Our bug, not CSS's — logged here only because it's the same "multi-pod behavior is easy to get subtly wrong" theme as several entries above.
